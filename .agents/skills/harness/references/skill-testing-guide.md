## 1. Test Framework Overview

Skill quality verification combines **qualitative evaluation** and **quantitative evaluation**.

| Evaluation Type | Method | Suitable Skills |
|----------------|--------|-----------------|
| **Qualitative** | User directly reviews output | Tone, design, creative work — subjective quality |
| **Quantitative** | Assertion-based automated scoring | File creation, data extraction, code generation — objectively verifiable |

Core loop: **Write → Execute test → Evaluate → Improve → Re-test**

## 2. Writing Test Prompts

### Principles

Test prompts must be **concrete, natural sentences that actual users would type**. Abstract or artificial prompts have low testing value.

### Bad Examples

```
"Process a PDF"
"Extract data"
"Generate a chart"
```

### Good Examples

```
"In my Downloads folder there's 'Q4_Revenue_Final_v2.xlsx'. Add a profit
margin (%) column using column C (revenue) and column D (costs). Then sort
descending by profit margin."
```

```
"Extract the table on page 3 of this PDF and convert to CSV. The table
header spans 2 rows — first row is category, second row is actual column names."
```

### Prompt Diversity

- Mix **formal / casual** tone
- Mix **explicit / implicit** intent (directly naming file formats vs requiring context inference)
- Mix **simple / complex** tasks
- Some should include abbreviations, typos, casual expressions

### Coverage

Start with 2~3 prompts, designed to cover:
- 1 core use case
- 1 edge case
- (optional) 1 composite task

## 3. Execution Testing: With-skill vs Baseline

### 3-1. Comparison Execution Structure

For each test prompt, spawn two sub-agents **simultaneously**:

**With-skill execution:**
```
Prompt: "{test prompt}"
Skill path: {skill path}
Output path: _workspace/iteration-N/eval-{id}/with_skill/outputs/
```

**Baseline execution:**
```
Prompt: "{test prompt}"  (identical)
Skill: none
Output path: _workspace/iteration-N/eval-{id}/without_skill/outputs/
```

### 3-2. Baseline Selection

| Situation | Baseline |
|-----------|----------|
| New skill creation | Same prompt without the skill |
| Existing skill improvement | Previous skill version (preserve snapshot) |

### 3-3. Capturing Timing Data

**Immediately** save `total_tokens` and `duration_ms` from sub-agent completion notifications. This data is only accessible at notification time and cannot be recovered later.

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

## 4. Quantitative Evaluation: Assertion-Based Scoring

### 4-1. Writing Assertions

When outputs are objectively verifiable, define assertions for automated scoring.

**Good assertions:**
- Objectively determinable as true/false
- Descriptive names so the result alone clarifies what's being checked
- Validates the skill's core value

**Bad assertions:**
- Always pass regardless of skill presence (e.g., "output exists")
- Require subjective judgment (e.g., "well written")

### 4-2. Programmable Verification

When assertions are code-verifiable, write them as scripts. Faster than manual checking, more reliable, and reusable across iterations.

### 4-3. Beware Non-Discriminating Assertions

Assertions that "pass 100% in both configurations" fail to measure the skill's differentiating value. When such assertions are found, remove them or replace with more challenging ones.

### 4-4. Scoring Result Schema

```json
{
  "expectations": [
    {
      "text": "Profit margin column added",
      "passed": true,
      "evidence": "Column E 'profit_margin_pct' confirmed"
    },
    {
      "text": "Sorted descending by profit margin",
      "passed": false,
      "evidence": "Original order preserved, no sorting applied"
    }
  ],
  "summary": {
    "passed": 1,
    "failed": 1,
    "total": 2,
    "pass_rate": 0.50
  }
}
```

## 5. Leveraging Specialist Agents

Using specialist agents in the testing/evaluation process improves quality.

### 5-1. Grader

Performs assertion-based scoring and extracts verifiable claims from outputs for cross-validation.

**Role:**
- Pass/fail judgment per assertion + evidence
- Extract and verify factual claims from outputs
- Feedback on eval quality itself (flag assertions that are too easy or ambiguous)

### 5-2. Comparator (Blind)

Anonymizes two outputs as A/B and judges quality without knowing which used the skill.

**When to use:** When you want rigorous confirmation that "the new version is truly better." Can be skipped for routine iterative improvement.

**Judgment criteria:**
- Content: accuracy, completeness
- Structure: organization, formatting, usability
- Overall score

### 5-3. Analyzer

Analyzes statistical patterns in benchmark data:
- Non-discriminating assertions (both configs pass → no differentiating power)
- High-variance evals (results vary wildly between runs → unstable)
- Time/token tradeoffs (skill improves quality but also increases cost)

## 6. Iterative Improvement Loop

### 6-1. Collecting Feedback

Show outputs to the user and collect feedback. Empty feedback = "no issues."

### 6-2. Improvement Principles

1. **Generalize the feedback** — narrow fixes for specific examples are overfitting. Fix at the principle level.
2. **Remove what doesn't carry its weight** — read transcripts; if the skill makes agents do unproductive work, delete that part.
3. **Explain Why** — even if user feedback is brief, understand why it matters and reflect that understanding in the skill.
4. **Bundle repetitive work** — if every test run generates the same helper script, pre-include it in `scripts/`.

### 6-3. Iteration Procedure

```
1. Modify skill
2. Re-run all test cases in a new iteration-N+1/ directory
3. Present results to user (with comparison to previous iteration)
4. Collect feedback
5. Modify again → repeat
```

**Exit conditions:**
- User is satisfied
- All feedback is empty (all outputs have no issues)
- No meaningful improvement remains

### 6-4. Draft → Review Pattern

When modifying skills: draft first, then **re-read with fresh eyes** and improve. Don't try to write perfectly in one pass; use draft-review cycles.

## 7. Description Trigger Verification

### 7-1. Writing Trigger Eval Queries

Write 20 eval queries — 10 should-trigger + 10 should-NOT-trigger.

**Query quality criteria:**
- Concrete, natural sentences actual users would type
- Include specific details: file paths, personal context, column names, company names
- Mix length, tone, format
- Focus on **boundary cases (edge cases)** over clear-cut answers

**Should-trigger queries (8~10):**
- Same intent in varied expressions (formal/casual)
- Cases where the skill/file type is implied but not explicitly named
- Non-mainstream use cases
- Cases competing with other skills where this skill should win

**Should-NOT-trigger queries (8~10):**
- **Near-miss is key** — similar keywords but a different tool/skill is appropriate
- Obviously unrelated queries ("write a fibonacci function") have no testing value
- Adjacent domains, ambiguous expressions, keyword overlap but different context

### 7-2. Existing Skill Conflict Verification

Verify the new skill's description doesn't overlap with existing skills' trigger domains:

1. Collect descriptions from existing skill list
2. Verify the new skill's should-trigger queries don't incorrectly trigger existing skills
3. If conflicts found: clarify boundary conditions in the description

### 7-3. Automatic Optimization (optional advanced)

When description optimization is needed:

1. Split 20 eval queries into Train (60%) / Test (40%)
2. Measure trigger accuracy with current description
3. Analyze failure cases, generate improved description
4. Select best description based on Test set (not Train set — prevents overfitting)
5. Max 5 iterations

> This process uses automated scripts with `claude -p`. Token cost is high, so run only as a final step once the skill is sufficiently stable.

## 8. Workspace Structure

Directory structure for organized management of test/evaluation results:

```
{skill-name}-workspace/
├── iteration-1/
│   ├── eval-descriptive-name-1/
│   │   ├── eval_metadata.json
│   │   ├── with_skill/
│   │   │   ├── outputs/
│   │   │   ├── timing.json
│   │   │   └── grading.json
│   │   └── without_skill/
│   │       ├── outputs/
│   │       ├── timing.json
│   │       └── grading.json
│   ├── eval-descriptive-name-2/
│   │   └── ...
│   └── benchmark.json
├── iteration-2/
│   └── ...
└── evals/
    └── evals.json
```

**Rules:**
- Use **descriptive names** for eval directories (e.g., `eval-multi-page-table-extraction`), not numbers
- Preserve each iteration in an independent directory (never overwrite previous iterations)
- Do not delete `_workspace/` — for post-hoc verification and audit trail
